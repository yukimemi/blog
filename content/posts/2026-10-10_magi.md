**magi — Chat で頼むだけで、設計・実装・レビュー・PR・リリースまで複数のエージェントがつないでくれる CLI**

![magi demo (desktop)](https://raw.githubusercontent.com/yukimemi/magi/main/assets/demo-desktop-ja.gif)

claude や codex といったエージェント CLI を複数使って、頼んだ作業を設計からリリースまで進めてもらうツール **magi** を Rust で作りました。人間がやることは、基本的に Chat で頼むことと、聞かれたことに答えること、最後にマージを承認することです。

https://github.com/yukimemi/magi

## なぜ作ったのか

エージェントに実装を任せられるようになっても、その前後は意外と人間がつないでいます。

1. **頼む前の整理**：何を作るかが曖昧なまま投げると、出てきたものの良し悪しも判断できない。
2. **設計・レビューの手間**：最初の設計方針が一本だけだと、それが外れていたときにレビューで直しきれない。レビューの観点も、1 人のエージェントでは偏る。
3. **PR からあとの確認**：PR を作る、CI を見る、指摘に対応する、リリースの version を上げる、といった作業を結局自分で見張っている。
4. **離席中に止まる**：エージェントが判断に迷って止まっていても、PC の前にいないと気づけない。

これらを「頼んだら、あとは必要なときだけ呼ばれる」形にしたくて作ったのが magi です。subscription 契約の CLI（`claude` / `codex` / `opencode` / `agy` / `omp`、または任意のコマンド）をそのまま動かす仕組みなので、既存のプランの範囲で動き、API キーは要りません。

## magi の主な特徴

### 1. 頼むのは Chat だけ

`magi web` で起動するスマホ向けの UI に **Chat** があります。リポジトリを読んだりコマンドを実行したりできるエージェントと、作りたいものを相談します。やりたいことの形が固まったら「タスクとして登録して」と伝えると、エージェントが会話の中から `magi task add --solo`（単独実装）を実行してくれます。会話ごとに、2〜3 人の implementers で競わせる設定へ切り替えることもできます。

- 会話は Chat のまま続くので、1 つ登録して終わりではなく、あとから別の作業を頼めます。
- Chat は既定では書き込み禁止で動きます（会話の途中でリポジトリが変わると、あとの比較ができなくなるため）。

登録されたタスクは `magi serve` / `magi web` のループが 1 つずつ取り出して実行します。ターミナルから `magi run "add retries to the uploader"` のように直接頼むこともできます。

### 2. advisors が設計を出し、synthesizer が 1 本にまとめる

実装の前に **advise** という段階があります。

- **advisors**（既定 3 人）が、それぞれ read-only で設計案を出します。
- **synthesizer** が、その案の良いところを混ぜて 1 つの設計方針にまとめます。

synthesizer は、各案の良い部分を 1 本の方針に統合します。どれが勝つかは決めません。実装者にはこの方針が渡ります。`[graph] advise` で on / off できます。

### 3. implementers が実装し、judges が投票する

方針をもとに **implementers** が実装します。競争モードで複数の implementers を動かすと、候補は A / B / C のようにラベル化され、**judges** が順位を付け、意見が割れれば議論したうえで投票します。judges は誰が書いたかを知らずに採点します（ブラインドにするのが元々の出発点でしたが、この記事の主題ではないので詳細は README に譲ります）。

なお、`[graph] implementers` の既定値はコード（`src/config.rs`）では 1 です。Chat から出すタスクも既定は Solo（`magi task add --solo`、単独実装）ですが、Chat 画面のセレクトで会話ごとに Solo / 2 implementers / 3 implementers を選べます。2 か 3 を選ぶと、エージェントは `--solo` なしの `magi task add --implementers N` でタスクを出します。CLI では `magi run --implementers N`（短縮形 `-c`）や `[graph] implementers` で人数を増やして競争を指定できます。README の表には「既定 3」とある箇所がありますが、実際のコードの既定とは異なるので、ここではコードを正としています。

### 4. reviewers と fixer のレビューループ

実装を勝ち残らせたら、次は有限回のレビューループです。

1. 各 **reviewer** には、レビュー対象のコミットに固定された専用の detached worktree が渡されます。レビュー中に作業ツリーが変わることはなく、fixer と競合もしません。
2. `[verify] e2e` に書いたコマンドが worktree で実行され、その出力が fixer に渡されます。
3. **fixer** が blocking な指摘を直します。ただし、確認できる根拠があれば、指摘を**根拠つきで却下**することもできます。
4. 指摘がなくなり検証も通るか、`review_rounds` を使い切るまで繰り返します。

finding の id（`R2-1-3` のような形式）はエージェントではなく magi が振ります。fixer の対応報告をこの id で突き合わせられるので、reviewer の精度を集計して確かめられます。また、タイムアウトなどで reviewer が答えなかったラウンドは「指摘なし」とは見なされません。

### 5. PR・gate・e2e・リリースまでを通す

`merge = "pr"` のときは、実装の最後に magi が PR を開き、そのまま見張り続けます。

- CI の結果と、人間・bot 双方のレビューコメントを読み、必要なら fix ラウンドを回して push します。`[graph] land`（既定 on）の領域です。
- マージ前には `[verify] gate` に書いたコマンドがすべて exit 0 になる必要があります。`gate` を CI と同じコマンドにしておけば、ローカルで通れば PR も緑になります。
- 強制マージはしません。ラウンドを使い切ったら、何が失敗しているかをコメントして PR を開いたままにします。

マージが済んだあとのリリースにも関わります。Rust リポジトリ（base ブランチのルートに `Cargo.toml` がある場合。ない場合はスキップ）では、`[merge] release_bump`（既定 on）により、変更内容から major / minor / patch のどの桁を上げるかを magi が判断し、`chore/release-vX.Y.Z` という version bump の PR を開きます。どのリポジトリでも公開まで進むわけではありません。その先は `[release] mode` で分かれます。

- **`actions`（既定）**：version bump の PR は automerge が設定され、CI が通ればそのままマージされます。つまりこの PR には、実装 PR のような個別の承認の質問は付きません。マージ後は、リポジトリ側の `auto-tag.yml` がタグを push し、そのタグで `release.yml` が公開します。この構成ではタグを打つのは magi ではありません。
- **`local`**：Actions が動かないリポジトリ向けの opt-in です。automerge は設定されず、リリース PR のマージも所有者の承認（`merge` / `hold` の質問）を待ちます。承認されてマージされたあとは、magi 自身がタグを作って push し、`[release] commands` に書いたコマンド（`cargo build --release` や `gh release create` など）を順に実行して公開します。

### 6. 分からないときは Question で聞かれる。マージは承認が先

途中で判断に迷ったエージェントは、推測で進めずに質問します。

```sh
magi ask --summary "Which storage backend?" --choice SQLite --choice Redis
```

これは**エージェントが**実行するコマンドで、答えが来るまで止まります。質問はスマホの UI に選択肢のボタンつきで表示され、押した答えがそのままエージェントの標準出力に返ります。ターミナルでは `magi answer` で同じ答えを返せます。質問には HTML で書いた確認画面（Panel）も添えられるので、diff や表を見ながら決められます。

![magi demo (phone)](https://raw.githubusercontent.com/yukimemi/magi/main/assets/demo-ja.gif)

実装した変更の PR のマージも同じ仕組みです。`[graph] land_approval` は既定で on で、マージ前に「何が入るか」を並べた質問が来ます。**沈黙は保留**として扱われ、何も答えなければマージされません。なお、上で書いたとおり、`actions` モードの version bump PR は CI が通れば自動でマージされる点は別扱いです。設定で変えられますが、無人でマージさせるには `land` と `land_approval` の両方を意図して切り替える必要があり、既定の挙動はあくまで「実装した変更の最後の一歩は人が決める」です。

## インストールと使い方

### インストール

```sh
cargo install magi-cli
```

### クイックスタート

```sh
magi init      # 最初の magi.toml を書き出す
magi doctor    # CLI やリポジトリ、roster の確認
magi web       # スマホ向け UI。新しい作業は Chat から始まる
magi serve     # キューを無人で回す
```

`[verify] gate` と `[verify] e2e` は、そのリポジトリで実際に確認したいコマンドに合わせて `magi.toml` に書きます。

## おわりに

自分にとって一番大きいのは、「頼む」と「承認する」の間を自分で埋めなくてよくなったことです。判断が必要なところだけスマホに通知が来て、それ以外は進んでいます。
